## 0. 原始数据（真实）

## 1. 边际成本效率  =  ΔRecall@5(百分点) / Δ成本(%)

> 成本 = 平均检索延迟。以「百分点 / 成本%」表达；因 bm25 基线延迟≈0，% 形式会放大，
> 同时给出「百分点 / 毫秒」的绝对值以便直观。

| 跃迁 | ΔR@5 | Δ延迟(ms) | Δ成本(%) | 边际效率(主) | 边际效率(绝对值) |
|---|---:|---:|---:|---:|---:|
| bm25 → hybrid | +4.35 pp | +12.35 | +2435% | 0.00179 pp/1% | **0.352 pp/ms** |
| hybrid → hybrid_rerank | **−2.18 pp** | +1264.95 | +9835% | **−0.00022 pp/1%** | **−0.0017 pp/ms** |

**解读**：
- bm25 → hybrid 是正向、划算的跃迁：每多花 1ms 检索算力换来约 0.35pp R@5。
- hybrid → hybrid_rerank 是**负边际效率**：多花 ~99 倍延迟，R@5 反而掉 2.18pp。
  → 在「检索算力」维度，hybrid 位于 **Pareto 前沿**，rerank 被严格支配。

## 2. 路由后混合成本  =  Σ(意图占比 × 该意图所选方案的单次成本)

> 用户原意：对比「全量开 Graph/重排」与「按需路由」。
> 因 Graph 臂未实测，此处用同等昂贵的「全量开 rerank」作对照（已是真实数据里的昂贵选项）。

### 2a. 全量 vs 路由（实测均值）
- **全量 always hybrid_rerank**：平均 1277.81 ms
- **推荐 always hybrid（=路由到最优单臂）**：平均 12.86 ms
- **混合成本比** = 1277.81 / 12.86 ≈ **99.4×（即路由方案成本仅为全量重排的 ~1%）**
- 且路由方案 R@5 更高（58.70 vs 56.52）→ 既省又准。

### 2b. 按类别路由（per-category R@5，retrieval_v2 latest）
| 类别 | bm25 R@5 | hybrid R@5 | 差异 |
|---|---:|---:|---:|
| colloquial | 0.25 | 0.50 | hybrid +0.25 |
| direct_rule | 0.333 | 0.333 | 持平 |
| special_case | 0.60 | 0.60 | 持平 |

路由策略：**bm25 用于 direct_rule / special_case（R@5 与 hybrid 持平，成本 0.42ms），hybrid 仅用于 colloquial**。
若三类查询各占 1/3（分布为假设值，非实测）：
- 路由延迟 ≈ (⅓×0.42)+(⅓×0.42)+(⅓×13.86) ≈ **4.90 ms**
- vs 全 hybrid 13.86 ms → **再降 ~65%**，colloquial 召回由 hybrid 保住。

> 说明：2b 的「1/3 分布」是示意假设；真实混合成本需按线上 query 分布加权。框架成立，加权值待补。

## 3. 成本结构拆解 + topk 旋钮

### 3a. 成本结构（输入/嵌入占绝对主导）
- 检索成本 **86.4% 花在 query_embedding（输入算力）**，融合/BM25/稠密打分合计 <14%。
- 这与「RAG 场景输入 token 占成本 80%+」的业界经验一致，且此处为**实测**而非经验值。
- 生成侧（LLM）输入 context token 占比为业界常识（检索上下文喂给 LLM），但本评测未插桩测 token，
  故不作为本仓库的实测结论引用。

### 3b. topk_to_llm 旋钮（final_top_k 5 → 3）
当前配置：`candidate_count=20`（重排候选）、`rerank_top_n=10`、`final_top_k=5`（喂给 LLM）。
R@K 曲线给出质量-成本权衡（governance hybrid）：

| final_top_k | R@3 | R@5 | 5→3 损失 | LLM 输入 context |
|---|---:|---:|---:|---:|
| 5 | 0.4783 | **0.5870** | — | 100% |
| 3 | — | ≈0.4783* | **−10.9 pp** | **−40%** |

\* R@3 即 top-3 命中率，作为 top_k=3 的质量下界近似。
- **结论**：`final_top_k` 5→3 仅损失 ~7.7–10.9 pp R@5，却把喂给 LLM 的上下文削减 **40%**
  （直接降低生成侧输入 token 成本）。这是一个**真实、可调的成本/质量旋钮**。
- 同理，`rerank_top_n` 10→5 可把重排调用减半（若启用重排）。

## 简历可用要点（诚实版，建议照此措辞）

1. **检索成本效率**：在报销制度 QA 语料上做 4 策略真实消融，
   hybrid(BM25+Vector) 以 ~13ms 平均延迟取得最高 R@5(0.587)，
   而加 Cross-Encoder 重排延迟飙到 ~1278ms（约 99×）且 R@5 反降 →
   据此将重排设为按需可选而非默认，检索成本降约 **99×** 无召回损失。
2. **成本结构**：分阶段延迟剖析显示检索算力 **86% 集中在查询嵌入（输入）阶段**，
   据此把优化重心放在嵌入/上下文裁剪（topk 5→3 砍掉 40% 喂 LLM 上下文）而非重排。
3. **可调旋钮**：`final_top_k` 5→3 仅损失 7.7–10.9 pp R@5，换取 LLM 输入上下文 −40%，
   形成可量化的成本/质量权衡 dial。

> ⚠️ 不要写「美元/Token 成本节省 X%」——当前为延迟代理，token 成本需插桩复测。
