# UG-008 第一阶段：来源归属与 ACL 回填基础设计

**状态：** 已确认，待实施计划

**日期：** 2026-09-07
**范围：** 从当前 `main`（schema v15）选择性重建 UG-008 的第一阶段能力。本文不移植 PR #5 的 schema v8→v9 迁移实现，也不授权对业务数据库执行迁移或回填。

## 1. 目标与边界

MindGraph 的笔记必须可追溯到唯一、受控的知识来源；任何连接器只能写入和裁剪自己拥有的来源。ACL 回填的第一责任是发现不可信状态，而不是猜测归属后“修复”数据。

本阶段交付：

- 稳定、可注册的来源归属模型；
- 来源限定的 connector 同步和裁剪契约；
- 只读 dry-run 审计及结构化 finding；
- 在隔离 SQLite 数据库中的回归验证。

本阶段不交付：

- 对业务数据库执行的 apply、rollback 或自动回填命令；
- 治理 case、reconciliation、治理策略或检索/Chat 强制门禁；
- 管理员 API、Web 审核队列；
- 自动认领、删除或扩权任何历史笔记。

后续阶段顺序固定为：治理策略与 case/reconciliation → 检索/Chat 强制执行 → 管理 API 与渐进式 Web 队列。前一阶段没有独立验收，不得进入下一阶段。

## 2. 现状与兼容性约束

当前 schema v15 已在 `notes` 中保存 `source_id`、`source_path`、`acl_json` 和 `acl_public`，`VaultSyncService` 已按 `source_id` 写入并按来源边界裁剪。它缺少一个可持久审计、可验证路径边界的来源注册契约，因此调用方传入的 `source_id` 尚不足以构成治理边界。

新设计必须保留上述笔记字段及其现有消费者。不得以 PR #5 的旧 schema 版本、DROP 型 rollback 或直接复制旧 migration 服务替换当前迁移路径。

## 3. 架构与数据契约

第一阶段采用 additive schema v16：新增来源注册记录与审计运行记录，不删除、重命名或放宽现有列和表。

### 3.1 来源注册

每条来源注册至少包含：

- 不可变 `source_id`；
- 规范化的根路径或连接器定位符；
- 来源类型和 connector 标识；
- 启用状态；
- 创建、更新与最近审计时间。

规范化后的路径、connector 标识与 `source_id` 构成唯一归属契约。重复注册或重叠路径注册必须被拒绝；系统不得采用“后写覆盖前写”的规则。

### 3.2 笔记归属与 ACL

`notes.source_id` 与注册来源相匹配时，`notes.source_path` 必须位于该来源声明的边界内。`acl_json` 与 `acl_public` 继续是笔记的生效访问控制快照；来源注册不覆盖笔记 ACL。

历史笔记出现未知来源、路径越界、重叠声明或无法解析 ACL 时，系统只生成 finding：不得自动绑定来源、删除笔记、将笔记公开或以更宽 ACL 替代原 ACL。来源 ACL 策略之间的冲突判断属于第二阶段治理策略，不在本阶段虚构来源默认 ACL。

### 3.3 审计运行记录

每次 dry-run 产生一个可查询的运行摘要：运行 ID、来源、模式、起止时间、状态、计数、稳定 reason code 与不含正文/凭据的 finding 元数据。审计记录不保存笔记正文、完整 ACL 规则、Token 或连接串。

## 4. 执行流与失败语义

执行流固定为：

```text
注册来源 → Dry-run 审计 → 人工处置异常 → 来源限定同步 → 来源限定裁剪 → 审计留痕
```

1. 连接器或管理员受控路径注册、启用或停用来源。
2. Dry-run 只读比对来源注册与现有 `notes`，输出 findings 和摘要。
3. 人工在来源配置层处置异常；本阶段没有直接改写笔记的回填动作。
4. 同步前验证来源注册、connector 身份与规范化根路径。
5. 同步仅能 upsert 其 `source_id` 的笔记；裁剪仅能按 `(source_id, source_path)` 删除自己的历史条目。
6. 同步和审计均写入不含敏感内容的审计摘要。

以下情形必须 fail-closed：

| 条件 | 行为 |
| --- | --- |
| 来源不存在、停用或 connector 不匹配 | 拒绝同步和裁剪，保留现有笔记 |
| 笔记路径不在来源边界 | 拒绝写入，产生路径越界 finding |
| 两个来源声明同一路径或重叠根路径 | 拒绝注册或同步，产生来源冲突 finding |
| ACL 无法解析 | 保留原 ACL，不公开、不覆盖，产生 ACL finding |
| 历史笔记归属不明 | 仅报告 `needs_review`，不自动认领、删除或扩权 |

所有第一阶段操作默认 dry-run。任何未来的 apply/rollback 能力必须另行设计、在隔离数据库完成验证，并重新获得对 schema 与数据操作的授权。

## 5. 组件职责

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| 来源注册仓库 | 校验、持久化、查询稳定来源边界 | 写入笔记内容、决定 ACL |
| 来源归属审计服务 | 只读发现与分类 findings，生成审计摘要 | 自动修复或直接编辑 Markdown |
| `VaultSyncService` 适配层 | 在同步和裁剪前强制验证来源所有权 | 推测未知来源、跨来源清理 |
| 审计记录仓库 | 保存最小必要的运行摘要与 reason code | 保存正文、凭据或完整敏感 ACL |

每个组件只通过明确的值对象/服务接口通信；API 与 Web 不在本阶段引入，以免在规则尚未可证明生效时暴露“可操作但无效”的治理入口。

## 6. 测试与验收

测试必须在临时 SQLite 数据库运行，绝不以真实 Vault 或业务数据库充当测试目标。

| 类别 | 最低验收 |
| --- | --- |
| 正常 | 单一注册来源可完成 dry-run；其 connector 可同步并仅裁剪自己的笔记 |
| 异常 | 未注册/停用/connector 不匹配来源被拒绝；无效 ACL 不会变为公开；归属不明仅生成 finding |
| 边界 | 重叠根路径、跨来源抢写、跨来源裁剪、来源迁移和 dry-run 零写入均有回归测试 |
| 不变性 | 任一拒绝路径后，相关 `notes`、ACL 和其他来源数据保持原状 |
| 审计 | 每次审计有稳定 reason code、计数和摘要，且不含正文、凭据或完整 ACL 内容 |

第一阶段完成的发布门槛：相关 pytest 全绿、当前运行时 Ruff 致命错误 gate 通过、schema 兼容回归通过、隔离库中所有拒绝路径的状态不变断言通过。任何被跳过、依赖真实库或没有执行的项目必须明确报告，不得作为通过证据。

## 7. 风险与决策

- **风险：** 依据文件路径自动认领历史数据会把不确定性转换成越权。

  **决策：** 只读 finding + 人工处置，禁止自动认领。
- **风险：** 迁移旧 PR #5 的 schema 服务会把 schema v9 假设和 DROP 型 rollback 带入 schema v15。

  **决策：** 仅以当前 schema 的 additive v16 演进实现；不移植旧迁移服务。
- **风险：** 先做 UI 会产生未被检索/Chat 真正执行的治理假象。

  **决策：** API/UI 后置到检索强制执行完成之后。

## 8. 后续计划前置条件

本规范确认后，实施计划必须拆分为独立、可验收的变更：schema/数据仓库、来源审计、同步强制边界、隔离 SQLite 测试与发布验证。计划不得包含真实业务库操作；若实施需要 schema migration 或任何数据写入命令，必须在该实施开始前重新获得明确授权。
