# PR-04｜全量与增量切分一致性门禁

阶段：M0  
依赖：PR-03

## ⚠️ 现场核对修正（2026-09-11 实测，优先于下文）

**修正 1：98/69 不是「参数漂移」，是「同一语料的两条切分路径」。** 索引 metadata 是铁证：

| 索引版本（两者都在 `data/retrieval_indexes/`） | chunk 数 | metadata 记录的切分口径 |
|---|---:|---|
| `m3-20260910T073532Z-9befc0b7`（= 该根 CURRENT） | **69** | `chunk_size=500, chunk_overlap=50`（扁平，来自 `document_loader`） |
| `m4-20260909T123040Z-d432056c` | **98** | `chunker={'child_size':500,'parent_size':1200,'overlap':50}`（**`StructuredChunker`**） |

→ 本 PR 的职责不是「把参数对齐」，而是**阻断未经认可的口径切换**。

**修正 2：比较器必须先能容忍多套 metadata schema，否则一上手就崩。** 实测三种形态：

| | `m2-*` / `m3-*` | `m4-*` | `mg-*` |
|---|---|---|---|
| metadata key 数 | 9 | 19 | 12 |
| 切分字段 | `chunk_size` / `chunk_overlap` | `chunker{child_size,parent_size,overlap}` | **无** |
| 构建字段 | 无 | `build_status` / `previous_index_version` / `reused_embeddings` / `new_embeddings` | `strategy=mindgraph_incremental` + 同左 |

**字段缺失是常态，不是异常。** 比较器要按「字段存在才比」设计，不能假设 `chunk_size` 一定读得到。

**修正 3：两个根各是独立命名空间，且有 4 个版本目录根本没有 metadata.json。**

| 根 | CURRENT | 版本目录数 | 缺 metadata.json |
|---|---|---:|---:|
| `data/retrieval_indexes/` | `m3-20260910T073532Z-9befc0b7`（69 chunks） | 16 | 1 |
| `data/mindgraph_indexes/` | `mg-20260903T041848Z-4f9cdf5b`（581 chunks） | 7 | 3 |

三条由此得出：
1. **必须按 `(root, version)` 定位版本，不能只按版本名**——两根都有 `mg-` 前缀，但命名空间不同、chunk 数也不同。
2. 遇缺 metadata 的版本要**跳过并计数上报**，不是抛异常。
3. **不要跨根比较，也不要尝试统一。** 两根服务不同评测栈，`CURRENT` 各自独立。

**修正 4：口径取舍属产品决策，门禁不替产品选。** 69 与 98 哪个对，取决于 PR-03 的 policy 定论，
并牵扯线上索引是否重建。若现场发现必须选定一个才能继续，按 `04-PR-TEMPLATE.md` 的停止规则上报，
不要自作主张激活。

**修正 5（2026-09-11 夜补）：`m4` manifest 里的 `chunker` 是硬编码，PR-03 漏了这一处。**
`src/application/index_lifecycle_service.py:51` 写着
`"chunker": {"child_size": 500, "parent_size": 1200, "overlap": 50}` ——**字面量**，
不读 `ChunkingPolicy`。即 PR-03 收敛了三处，**这是第四处**。

对本 PR 的直接影响：门禁恰恰要读 manifest 的切分字段来判断口径。如果它是硬编码，
那么「配置了新 policy 但 manifest 仍写 500/1200/50」时，**门禁会被蒙蔽**——
它看到的是常量，不是实际生效的参数。

→ 本 PR 的比较器**必须同时接受 `chunking_policy`（PR-03 起的新字段）与 `chunker`**，
并按 `chunking_policy > chunker > chunk_size/overlap` 取优先级；
`chunker` 与 policy 的同步（让它也读 policy）属 PR-03 遗留、应随 PR-09 一起收口。

**修正 6（2026-09-11 夜补）：同一根内混了四套前缀，比"两根都有 mg-"更乱。**
实测 `data/retrieval_indexes/` 一个根里同时有：

| 前缀 | 版本数 | chunk | 切分字段 |
|---|---:|---:|---|
| `m2-` | 2 | 69 | `chunk_size`/`chunk_overlap` |
| `m3-` | 3 | 69 | `chunk_size`/`chunk_overlap`（**`CURRENT`**） |
| `m4-` | 4 | 98 | `chunker{500,1200,50}` |
| **`mg-`** | **6** | 254 / 266 / 303 / 303 / 581 / 610 | 无切分字段 |

即线上索引（`mg-`）的历史版本**被建到了 retrieval 根里**。这强化修正 3 第 1 条：
只能按 `(root, version)` 定位，任何"按前缀猜语义"的写法都会认错栈。

## 目标

同一语料和同一 ChunkingPolicy 经任意构建入口生成相同 document set、chunk ID、文本和 checksum。

## 真实业务失败

构建入口的解析、切分和范围口径可能漂移，导致同一知识库在重建方式不同后检索结果变化。

## 范围内

- 建立共享 fixture 和索引快照比较器。
- 比较文档覆盖、顺序无关 chunk 集、checksum、metadata 必需字段。
- 激活前运行一致性检查；不一致阻断 CURRENT 切换。
- 输出最小差异报告。

## 范围外

- 不要求向量浮点逐位一致。
- 不更改召回策略。

## 实施顺序

1. 获取最新 main SHA、git status 和现有基线。
2. 复现业务失败或证明当前缺口。
3. 先补失败测试与契约测试。
4. 实现最小兼容改动。
5. 运行目标测试、相关回归与必要评测。
6. 输出新旧差异、已知风险和回滚步骤。

## 测试矩阵

- 正常全量/增量一致。
- 缺文档、改参数、漏 metadata 均能被门禁捕获。
- 旧 CURRENT 在失败后保持不变。

## 验收标准

- 已知 98/69 漂移被消除或得到可解释且被产品认可的双口径。
- 意外缩水默认阻断。

## 回滚

关闭新 gate flag 后恢复旧激活流程；保留差异报告。
