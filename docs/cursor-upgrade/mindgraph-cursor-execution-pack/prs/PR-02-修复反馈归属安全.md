**修正 2：文件清单漏了一个，且它决定本 PR 是否真的生效。** 写入端两处不对称（实测）：

`src/application/agent_service.py`：在 :367 的 INSERT 中补 `principal_id` 列与占位符，

**修正 2b：认证口径 —— 写入端落库的是 `str`，查询端必须同源同口径。**
实测 `src/api/auth.py` 有**两个不同的主体出口**：

| 出口 | 位置 | 返回 |
|---|---|---|
| `require_authenticated(...)` | `src/api/auth.py:215` | **`dict`**（principal 字典，含 `name`/`roles`/`auth_mode`/`authenticated`） |
| `current_actor(request)` | `src/api/auth.py:257` | **`str`**（`principal.get("name") or principal.get("username") or "anonymous"`） |

写入端 `ChatService._persist_or_raise` 落库的是 **`str`**（`principal or "anonymous"`）。
因此查询端 `FeedbackService.create_feedback(..., principal_id: str)` **必须用 `current_actor` 口径**，
否则与存量行匹配不上。

**两种写法都可行，但鉴权面与测试注入行为不同 —— 选一个并保持自洽：**

| 写法 | 鉴权 | 主体口径 | 测试注入方式 |
|---|---|---|---|
| **A（推荐，实测已被采用）**<br>`Depends(require_authenticated)` + 函数体内 `principal_id=current_actor(request)` | ✅ 保留 | str ✅ | **patch `api.routes.feedback.current_actor`**（不是 `api.auth.current_actor`！见修正 4） |
| **B**<br>`Depends(current_actor)` | ⚠️ 需另行配置鉴权 | str ✅ | **必须用 `app.dependency_overrides[current_actor]`** —— `router` 在模块导入时即捕获函数对象 |

**⚠️ 两种写法都用 `from api.auth import current_actor`，所以都**不能**靠给 `api.auth.current_actor` 赋值来注入。**

**修正 4（实测铁证 · 2026-09-11 21:5x，优先于修正 2b）：`patch auth.current_actor` 对路由无效，这不是猜测。**

本仓实测（`PYTHONPATH=src` 直接跑）：

```
绑定前  fb.current_actor is auth.current_actor : True
patch 后 fb.current_actor is auth.current_actor : False
>>> patch auth.current_actor 对路由是否生效 : NO（无效）
```

**根因**：`src/api/routes/feedback.py` 写的是 `from api.auth import current_actor` ——
这在 `api.routes.feedback` **模块命名空间里建了一个独立的名字绑定**。
之后 `auth.current_actor = fixed_actor` 只改了 `api.auth` 的那个引用，**路由函数体里查到的仍是旧的函数对象**。
（这与 FastAPI 的 `Depends` 捕获函数对象是**两个独立的坑**，别混为一谈。）

**正确注入方式（二选一）：**

```python
# 方式 1：patch 路由真正绑定的那个模块（最贴合当前实现）
from api.routes import feedback as feedback_route
feedback_route.current_actor = lambda request: "user-a"

# 方式 2：改实现走 Depends，再用 dependency_overrides（更"FastAPI 正统"）
#   route: principal_id: str = Depends(current_actor)
app.dependency_overrides[current_actor] = lambda: "user-a"
```

**判别口诀**：`Depends(...)` 捕获的是**函数对象**（→ 用 `dependency_overrides`）；
`from X import f` 后在函数体里 `f()` 是**模块级名字绑定**（→ patch 使用方的模块，不是源模块）。

**⚠️ 红线警告（写给执行者）：这 6 个红是测试注入失效，不是实现有错。**
**绝对不要为了让测试变绿而削弱实现**——例如去掉 `WHERE ... AND principal_id=?` 的归属条件、
或把 fail-closed 改成 fail-open。那会直接击穿本 PR 的安全目标（跨主体越权读/写）。
判据：实现侧只需满足「`SELECT ... WHERE request_id=? AND principal_id=?` + 无 principal 时拒绝」，
测试侧的错误必须**在测试里**修。

**修正 4b（全量套件实测 · 2026-09-11 21:54）：6 个红 = 3 个独立缺陷，全部在测试侧。**

实测 `pytest -q --no-cov` → **6 failed / 671 passed / 3 skipped**，
失败**全部**落在 `tests/test_feedback_ownership.py`，仓库其余 669 个测试**零回归**
（`671 - 669 = +2`，正是本文件里已转绿的两个 agent 测试）。三个缺陷：

| # | 缺陷 | 位置 | 症状 | 修法 |
|---|---|---|---|---|
| 1 | **注入失效**（主因，影响 5 个路由测试） | `tests/test_feedback_ownership.py:64-65` | 真实 actor 取到 `"anonymous"`，与 seed 的 `'user-a'` 不匹配 | patch **`feedback_route.current_actor`** |
| 2 | **异常处理器缺失**（把所有断言的失败伪造成 500） | 同文件 `_app()` 里 `FastAPI()` 后 | `NotFoundError` 未注册处理器 → **500 而非 404** | 加 `@app.exception_handler(NotFoundError)` 映射 404，或直接从主应用取 handler 集合 |
| 3 | **入参类型不符** | 同文件 `:153` | `_payload()` 返回 `dict`，却传给 `create_feedback(payload: FeedbackCreate)` → `AttributeError: 'dict' object has no attribute 'request_id'` | 该处构造真实 `FeedbackCreate(**...)`，或改用路由调用 |

**注意 2 的方法论意义**：缺陷 2 会让「实现完全正确」的情况下也返回 500，
进而把**测试自身的问题**伪装成**服务端崩溃**。排查顺序应为：
先确认注入是否生效 → 再确认异常映射是否注册 → 最后才怀疑实现。

**修正 4c（22:05 复测 · 剩余 4 红 = 第 4 个缺陷 + 缺陷 3 未修）**

修掉注入目标（缺陷 1）后：**6 红 → 4 红 4 绿**。剩下的红暴露了**更隐蔽的一层**：

| # | 缺陷 | 症状 | 真因 |
|---|---|---|---|
| 4 | **`try/finally` 把 patch 撤销了** | 3 个「期望 201 得 **404**」 | 见下 |
| 3 | 入参类型不符（**未修**） | `AttributeError: 'dict' object has no attribute 'request_id'`（`feedback_service.py:30`） | `_payload()` 是 dict |

**缺陷 4 的真因（这是最容易误判成"实现 bug"的一处）：**

```python
original = feedback_route.current_actor
feedback_route.current_actor = fixed_actor
try:
    app = FastAPI()
    app.add_exception_handler(ProductError, product_error_handler)
    app.include_router(feedback_route.router, prefix="/api/v1")
    return TestClient(app, raise_server_exceptions=False)
finally:
    feedback_route.current_actor = original      # ← return 时 finally 立即执行，patch 被撤销
```

`try` 块内的 `return` **会先跑 `finally`**，所以 `TestClient` 拿到手时 patch 已经回滚 →
请求期间 `current_actor` 是**真实的那个** → 取到 `"anonymous"` → 与 seed 的 `'user-a'` 不匹配 → 404。
**`_app()` 返回的 client 从头到尾用的都是未打补丁的路由。**

**⚠️ 并且这是个「假通过陷阱」**：`test_other_principal_gets_uniform_not_found` 与
`test_null_owner_row_fail_closed` 期望 404，**在"一切都 404"的状态下会照常变绿**——
**绿得没有意义**。所以不能只看红灯数下降，必须看**每条断言是否因为正确的原因通过**。

**修法（推荐，最小且不留全局泄漏）**：把 `_app` 改成 pytest fixture，借 `monkeypatch` 自动回滚：

```python
@pytest.fixture
def make_client(monkeypatch):
    def _make(db, actor="user-a"):
        override_container(SimpleNamespace(database=db, feedback=FeedbackService(db)))
        monkeypatch.setattr(feedback_route, "current_actor", lambda request: actor)
        app = FastAPI()
        app.add_exception_handler(ProductError, product_error_handler)
        app.include_router(feedback_route.router, prefix="/api/v1")
        return TestClient(app, raise_server_exceptions=False)   # 不在 try 里 return
    return _make
```

（若坚持用普通函数，则**去掉 `try/finally`**——每次 `_app(...)` 都会重新打补丁，泄漏在本文件内无副作用；
但 fixture 写法更干净，评审不会挑。）

**缺陷 3 的修法**：`:154` 处不要传 dict，构造真实模型：
`service.create_feedback(FeedbackCreate(**_payload("req-own-5")), principal_id="user-a")`。

**修正 5：文件清单漏了第 4 个调用方（22:03 由执行者发现，核对方原清单有漏，特此补正）。**

`create_feedback` 在全仓共 **4 个调用点**，改签名前必须全部处理：

| # | 调用点 | 状态 |
|---|---|---|
| 1 | `src/api/routes/feedback.py:16` | 需传 `principal_id=current_actor(request)` |
| 2 | `src/application/agent_service.py`（`_persist_assist` 的 INSERT） | 写入端补列，见修正 2 |
| 3 | **`src/application/evidence_tools/feedback_tool.py:143`** | **原任务书与首次核对均漏列**；签名改 fail-closed 后此处必抛错 |

`feedback_tool.py` 内**已有可直接复用的主体口径**（`:80`）：
`current_user = (scope or {}).get("user") or "anonymous"` —— 与 `agent_service.py:174` 同一写法，
**不要另造第三个口径**（三处口径不一致正是本 PR 要消灭的东西）。

**这条的意义**：`create_feedback` 这类**签名收紧**型改动，风险不在被改的那个文件，
而在**调用方是否被穷尽**。落代码前必须 `grep -rn "create_feedback" src/ tests/` 把清单跑全，
再逐个判断「需改 / 走 HTTP 无需改」。**靠任务书的文件清单是会漏的。**




**修正 3：存量 NULL 与增量补写是两件事，策略要先定。** 下文「兼容历史 principal_id 为空的数据，默认 fail-closed」
指的是**存量**记录如何处理；修正 2 解决的是**增量**不再为 NULL。存量策略属产品决策
（全拒 / 一次性回填 / 仅放行匿名主体），且可能影响已有 bad-case 流程，
必须在现场核对报告里给出方案与影响面，再实现。

## 目标

只有问答所属 principal 才能提交反馈；跨主体请求不暴露 request_id 是否存在。

## 真实业务失败

当前 `/feedback` 仅检查 request_id 是否存在，认证用户可能对其他主体的问答写入反馈。
