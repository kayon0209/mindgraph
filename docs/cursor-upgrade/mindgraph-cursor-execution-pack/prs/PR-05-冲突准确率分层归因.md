## ⚠️ 现场核对修正（2026-09-11 实测）

**前提成立**：`conflict_accuracy: 0.0` 确在冻结基线产物中。

**三点提示**：

1. **该指标来自 offline 冻结预测集，不是 `/api/v1/evaluations` 的检索层 run。**
   `EvaluationService.execute()` 不调用答案层，所以归因必须走离线预测脚本，
   不要指望 API 跑得出这个数、也不要把它当成 API 的返回字段。
2. **`evaluation/answer_eval.py` 有 4 处存量 mypy 错误**（实测：`HEAD` 版与当前工作区版
   在 `:286` / `:306` / `:489` / `:490` 逐条相同）。改这个文件前先取 HEAD 版对比确认基线，
   验收报告里区分「存量」与「本次引入」，**不要顺手清债**（违反 guardrail §2）。
3. 本 PR 依赖 PR-01 的冻结基线产物，**PR-01 已提交**（本地 `483b0be`），可直接开工。

## 目标

把 conflict accuracy=0 的每个案例归因到召回、metadata、生命周期过滤、冲突检测或生成层。

## 真实业务失败

单一总分无法告诉开发者应该改检索、policy_key、日期过滤还是回答逻辑。

## 实施结果与归因结论（2026-09-11 夜，接管者实测）

**`conflict_accuracy = 0.0` 不是实现缺陷，系统侧真缺陷 0/6。**

### 证据链

| 事实 | 数值 | 来源 |
|---|---|---|
| 答案层 conflict_accuracy | **0.0**（6/6） | `baseline_20260911T113634Z.json` |
| 同类别检索层 recall@5 | **0.6667** | 同上 → **召回不差，问题在答案层口径** |
| 全库 `policy_key` 总数 | 11 | `data/product/product.sqlite3` → `notes` |
| **存在多版本的 key** | **仅 1 个：`expense.general`** | v1.0 `archived`+`effective_to=2026-06-30`；v2.0 `active` |
| 系统冲突判据 | 「同一 policy_key 有 **>1 个 active** 版本」 | `policy_conflict_service.py` `len(versions) > 1` |

→ 其余 10 个 key 全是单版本，这些案例**在定义上就不可能**检出版本冲突；
唯一有多版本的 `expense.general`，其 v1.0 已 `archived` 且过期，被**生命周期正确排除**。

### 归因分布（`scripts/attribute_conflict_cases.py` 产出）

| 主因 | 数量 | 含义 |
|---|---:|---|
| `lifecycle_filtered` | 5 | 历史版本已被归档/过期，系统按现行版本作答——**行为正确** |
| `eval_contract_mismatch` | 1 | 语料无版本并存；该案例实为**跨制度冲突**（餐补 vs 招待费） |
| **系统侧真缺陷** | **0** | 无一类归因到"该改代码" |

且逐案核对答案文本：**6 个案例系统都答对了**（"以 V2 为准"、"不得重复申领，扣 60 元"）。

### 🔴 待产品拍板（本 PR **不擅自决定**，也未改任何标签）

任务书「范围外」明写**不修改标签使案例通过**，故以下三项交产品决策：

- **A. 拆分 conflict 类别**：现类别混装了「版本演进」与「跨制度冲突」两种语义。
  建议拆成 `version_conflict`（期望 `conflicting_evidence`）与
  `cross_policy_conflict`（期望"识别并解释冲突"，不要求拒答）。
- **B. 或改指标口径**：`conflict_accuracy` 只在「同 key 多 active 版本」时才有意义，
  对该类以外的案例应记 `None`（不计分），而非恒 0。
- **C. 或实现跨制度冲突检测**：当前系统只实现版本冲突。这是**新能力**，
  不是 PR-05 范围内的"小型确定性缺陷修复"，应另立 PR。

**在拍板前，`conflict_accuracy = 0.0` 应解读为"指标口径不适用"，不得对外表述为系统缺陷。**
