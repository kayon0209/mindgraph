# Cursor 会话启动提示词

将下面内容与一个具体 PR 任务书一起发送给 Cursor：

```text
你正在修改 kayon0209/mindgraph。先不要写代码。

第一步：读取仓库根 AGENTS.md、docs/PRODUCT_STRATEGY.md、docs/UPGRADE_PLAN.md，
以及本执行包根目录的 05-FIELD-VERIFICATION.md（现场核对总览，优先于其余任务书），
再读本次 PR 任务书列出的文件和测试。

第二步：获取最新 main SHA、当前分支和 git status，确认任务书中的基线是否已过期。
git status 的三种现象，处理方式不同，不要一律当异常也不要一律忽略：
- `?? docs/cursor-upgrade/` 是本执行包自身 untracked，属预期，不要 add、不要删。
- **工作区若干净**：正常，直接开始。
- **工作区若仍有未提交改动**（含 A 类 PR-01 收尾加固、B 类评测栈数据集分派，以及可能存在的
  其它并行会话正在进行的改动）：按 05-FIELD-VERIFICATION.md 第 4 节处理。
  你**不得 checkout、不得 stash、不得 revert**，以工作区当前内容为权威，
  并在现场核对报告里**逐条声明**这些改动的类别与存在，说明它们不是本 PR 的产物。
  本 PR 的 diff 只应包含本 PR 自己的改动。
  **B 类归属（§4.1）尚未定案，但这不构成阻塞** —— B 类与执行包各 PR 无文件耦合，
  继续执行本 PR；归属决策推迟到本 PR 验收之后再统一处理。**不要停下等这个决策。**
分支：`pr-01-freeze-baseline` 只承载 PR-01 的交付物。若本 PR 尚未开工，从 `main` 新建分支；
**若已在该分支上开工，不要中断、不要搬家**，照常完成，并在报告里标注
「需在验收阶段整理提交归属」。

第三步：输出“现场核对报告”：当前实现、真实缺口、相关契约、潜在数据迁移、安全边界、最小改动方案、测试计划和回滚方案。
报告须包含一条声明：执行包阶段号（M0–M6）与 docs/UPGRADE_PLAN.md 的编号体系（UG-001…UG-008）不同，
仓库真正的实现顺序在 AGENTS.md:77「当前产品路线」。找不到 M0 不是异常，不要因此停下。

第四步：只有现场核对与任务书一致时才开始实现；如不一致，停止并列出差异，不得为了匹配任务书重写现有正确实现。
注意：执行包已完成一轮现场核对，**05-FIELD-VERIFICATION.md 第 6 节列出的全部前提修正均为实测结论，
应直接采信**（其中 PR-02/03/04/09 是任务书事实性错误，PR-05/06/07/08/12/13 是数据与工程前提补充）。
除此之外若发现新的不一致，照常停止并上报。

全程遵守 01-GLOBAL-GUARDRAILS.md：
- 一次只完成本 PR；不顺手开发后续 PR。
- 不改 Golden 标签、不降低安全门禁、不伪造测试输出。
- 不引入开放式多 Agent，不默认开启 Graph，不用换向量库掩盖召回问题。
- 所有数据库/API/SSE/索引变化都必须兼容或有明确迁移与回滚。

验收命令必须按 02-QUALITY-GATES.md 修正后的版本执行，三条陷阱勿踩：
- pytest 目标测试必须加 --no-cov（否则被 --cov-fail-under=55 判失败）；
- ruff 必须加 --select F821,F822,F823,E902（否则 5934 条存量债务会淹没你的改动）；
- mypy 报错若落在你未修改的文件上，先 git show HEAD:<file> 确认为存量。

结束时必须输出：
1. 修改文件及目的；
2. 测试命令和真实结果；
3. 新旧行为/指标对比；
4. 未完成项和已知风险；
5. 回滚步骤；
6. 建议的 commit message。
```
